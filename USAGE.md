# LyServer Dispatcher — Stage 1 (перевірки + попередній перегляд) і Stage 2 (кероване виконання)

Усі файли запуску лежать у `tools\dispatcher\`. Потрібен Windows PowerShell 5.1,
налаштовані `git`, `gh` (авторизований) та `opencode`.

## 1. Налаштування `config.psd1` (один раз)

`config.psd1` містить локальні налаштування і **не комітиться** (у `.gitignore`).

```powershell
cd C:\Users\Admin\Documents\LyServer\tools\dispatcher
Copy-Item config.example.psd1 config.psd1
notepad config.psd1
```

Перевірте значення: `RepoPath`, `GitHubRepo`, `ExpectedRemote`, `Model`,
`LogDir` (журнали мають бути **поза** репозиторієм), `RunRootDir`, `LockDir`.
Секретів у конфігурації немає і бути не повинно.

### Параметри Stage 2 (усі необов'язкові; старі конфіги працюють без змін)

| Ключ | За замовчуванням | Призначення |
|---|---|---|
| `TaskSource` | `GitHub` | `GitHub` — завдання зчитуються через `gh` (read-only); `Local` — тестовий режим, JSON-файл, **жодного** звернення до GitHub. |
| `AgentCommand` | `opencode` | Команда-виконавець (просте ім'я з `PATH`: літери, цифри, `. _ -`). Викликається як `<cmd> run --model <модель> <промпт>` з робочим каталогом = worktree завдання. |
| `LocalTaskFile` | `''` | Обов'язковий, якщо `TaskSource = Local`: шлях до JSON-масиву задач `[{"number":901,"title":"…","state":"open","labels":["ready-for-opencode"],"body":"…"}]`. |
| `BaseBranch` | `''` | Обов'язковий, якщо `TaskSource = Local`: базова гілка, з якої створюється worktree. У `GitHub`-режимі базова гілка береться з API (`default_branch`). |
| `LockStaleSec` | `900` | Поріг віку (секунди) для lock-файлів, чий власник неможливо підтвердити локально: чужий/невідомий хост або неповний/нечитабельний вміст. Живий локальний процес ніколи не визнається застарілим через вік (див. п. 4.1). |
| `TaskTimeoutSec` | `1800` | Тайм-аут виконання виконавця в Stage 2 (дерево процесів убивається у Windows). |
| `RunRootDir` | — | Каталог, де створюються worktree задач (має бути **поза** репозиторієм). |
| `LockDir` | — | Каталог lock-файлів (має бути **поза** репозиторієм). |

## 2. Тести

```bat
tools\dispatcher\Test-Dispatcher.bat
```

Код завершення `0` — усі тести пройдено; ненульовий — є помилка (код друкується
в кінці). Реальний репозиторій має залишитися **незмінним** відносно знімка,
зробленого на старті: коміти, stash чи приховування змін індексом
(`skip-worktree` / `assume-unchanged`) не потрібні, не використовуються і
перевіряються (T0, T40c).

**Реальний OpenCode у тестах НЕ запускається взагалі:** навіть model ping
Stage 1 виконує фіктивний `fakeagent-ping`, всі задачі Stage 2 виконують
фіктивні `fakeagent-*.ps1`, а зонд формату читає лише `run --help` фіктивного
агента. Реальний GitHub (читання через `gh`) і реальний локальний клон
використовуються лише для read-only перевірки незмінності.

Склад тестів:

- **T0** — знімок стану реального репозиторію (baseline) + перевірка відсутності
  прихованих індексних прапорців + підготовка **тимчасового** stage-1
  репозиторію (`git init` + потрібний origin); сам dispatcher у тестах ніколи
  не виконується проти реального репозиторію;
- **T1–T15** — Stage 1: квотування аргументів, точність `PONG`, пошук інструментів,
  валідація конфігурації, брудне дерево (стоп перед ping), тайм-аути ping,
  недоступна модель, повний preview-прогін, незмінність Issues/PR у GitHub,
  межі `Test-PathInside`, вбивство дерева процесів по тайм-ауту, порядок етапів,
  запуск BAT через cmd.exe, типи команд;
- **T16–T33** — Stage 2: життєвий цикл lock (паралельний запуск, застарілий
  lock, звільнення, живий PID + старий вік lock → відмова), створення/очищення
  worktree на **тимчасовому локальному** git-репозиторії, розбір і звірка `base-sha`,
  сканування недовіреного тексту, повні прогони Stage 2 фіктивним агентом
  (SUCCESS / NO_CHANGES / REFUSED / ERROR / TIMEOUT), відновлення після помилки,
  **збереження worktree і файлів агента після ERROR і TIMEOUT** (окремі тести),
  **відмова при невдалих командах верифікації** (стан невідомий → без успіху),
  облік staged/modified/untracked, збереження worktree за невідомого стану,
  вбивство дочірнього процеса по тайм-ауту, блокування активним lock, статична
  перевірка відсутності push/PR/мутацій GitHub у коді;
- **T35–T39** — **живий вивід агента**: проміжний рядок видно у консолі ДО
  завершення процесу (тест спостерігає за живим stdout-каналом самого
  диспетчера), stdout/stderr не губляться, той самий вивід лежить у журналі
  з часовими мітками `[OUT]`/`[ERR]`; фіктивний агент із паузами друкує рядки
  і пише в stderr і завершується успішно, з помилкою (exit code дитини
  зберігається точно) і по тайм-ауту (рядки до вбивства дерева збережені);
  вибір формату виводу (`--format json` після зонду `run --help` чи PLAIN
  fallback) і юніт-тести зонду (успіх / відсутність прапорця / помилка help /
  тайм-аут зонду);
- **T40** — фінальні інваріанти: незмінність Issues/PR у GitHub, збіг
  реального репозиторію зі знімком T0, відсутність прихованих індексних
  прапорців, чистота тимчасових репозиторіїв **і відсутність зайвих
  `dispatcher-*.log` у каталозі запуску тестів** (T40e; знімок таких файлів
  робиться в T0). Раніше тест T6 через збіг імені змінної (`$logFile` проти
  `$script:LogFile` — у PowerShell регістр ігнорується) підміняв файловий sink
  `Write-Log`, і T16 створював у каталозі запуску сторонній
  `dispatcher-<час>.log`; ім'я змінної T6 перейменовано на `$t6LogFile`.

Тести Stage 2 працюють із тимчасовим локальним git-репозиторієм та фіктивними
агентами (`fakeagent-*.ps1` у тимчасовому каталозі PATH); реальний GitHub-проєкт
не змінюється, реальна задача через OpenCode не запускається.

## 3. Запуск Dispatcher

### Stage 1 — лише попередній перегляд (типово)

```bat
tools\dispatcher\Start-Dispatcher.bat
```

Обидва BAT можна запускати з будь-якого поточного каталогу (шляхи обчислюються
від `%~dp0`).

Звичайний запуск виконує лише: перевірки середовища → ping моделі → пошук
Issue з міткою `ready-for-opencode` → повідомлення про кандидатів. Він **не
виконує інструкції з Issue, не змінює Issues/мітки і не створює гілок чи PR**.

### Stage 2 — кероване виконання (окремий ключ `-Stage2`)

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\dispatcher\dispatcher.ps1 -ConfigPath tools\dispatcher\config.psd1 -Stage2
```

`-Stage2` — єдиний спосіб увімкнути виконання. Конфіг не має ключа, який міг би
увімкнути push/PR/мутації GitHub: їх у коді просто немає.

**Живий вивід.** Вихідний потік агента (stdout і stderr) транслюється в
консоль і в журнал **під час виконання**, з мітками часу, а не після завершення
процесу. Приклад рядків у журналі:

```
2026-10-14 16:57:21 [OUT] {"type":"step_start", ...}
2026-10-14 16:57:21 [ERR] some warning from the agent
```

Рівні `OUT`/`ERR` означають відповідно stdout і stderr агента; рядки, які
пише сам dispatcher, мають рівні `INFO`/`WARN`/`ERROR`. Трансляція не змінює
тайм-аутів і кодів завершення: timeout досі вбиває дерево процесів і дає
код `2`, результати `SUCCESS/NO_CHANGES/ERROR/TIMEOUT/REFUSED` незмінні.

## 4. Життєвий цикл завдання (Stage 2)

1. **Lock.** `Enter-DispatcherLock` створює `dispatcher.lock` (PID, хост, час) у
   `LockDir`. Застарілість визначається за правилами (у такому порядку):
   **(1)** повний вміст + цей хост + **живий PID** → lock активний, **вік
   ігнорується** (тривала робота ніколи не втрачає lock через вік);
   **(2)** цей хост + мертвий PID → застарілий, забирається одразу, без
   очікування; **(3)** чужий/невідомий хост → застарілий лише за віком >
   `LockStaleSec`; **(4)** неповний (створюється іще без PID) або нечитабельний
   вміст → застарілий лише за віком, що захищає вікно «створення → запис» від
   паралельного перехоплення. Застарілий lock **архівується**
   (`.lock.stale-<час>-<суфікс>`, не видаляється) і береться заново; перед
   архівацією вміст перечитується і звіряється — якщо lock змінився або зник
   (інший екземпляр виграв гонку), рішення переоцінюється, чужий свіжий lock не
   перехоплюється.
2. **Повторна перевірка задачі.** Номер, стан `open`, наявність мітки
   `LabelReady` і відсутність `LabelInProgress` зчитуються з джерела ще раз
   безпосередньо перед виконанням (у `GitHub`-режимі — через `gh issue view`).
3. **Скан недовіреного тексту.** Опис Issue (недовірені дані!) перевіряється на
   заборонені директиви: `git push`, `gh pr/label/issue`-мутації, force push,
   `reset --hard`, прохання «створи PR», «закрий issue», «додай мітку» тощо.
   Будь-яке влучання → **відмова, код 4**. Обходу не існує: текст Issue не може
   скасувати правила безпеки, дозволити push, змінити конфіг або надати дозволи
   на GitHub-операції.
4. **База.** `git rev-parse <база>^{commit}` у головному клоні; у `GitHub`-режимі
   базою є `origin/<default_branch>`. Якщо в тексті задачі є маркер
   `base-sha: <hex>` — SHA звіряється з перевіреною базою (за префіксом).
   Невідповідність (напр. вимагають `054ef0a`, а база інша) → **відмова,
   код 4**, worktree не створюється.
5. **Worktree.** `git worktree add -b opencode/issue-<номер> <шлях> <базовийSHA>`
   у `RunRootDir` (поза репозиторієм). Існуючий шлях або гілка → відмова,
   повторного використання немає.
6. **Виконання.** `<AgentCommand> run --model <модель> <промпт>` з робочим
   каталогом = worktree, тайм-аут `TaskTimeoutSec`. Перевищення → вбивство
   **дерева процесів** Windows (`taskkill /T /F`), результат `TIMEOUT`, код 2.
   Промпт містить жорсткі правила і живиться текстом задачі у рамці
   `BEGIN/END UNTRUSTED TASK TEXT`.
   Перед запуском dispatcher **звіряє можливості CLI**: `<AgentCommand> run
   --help` (робочий каталог — каталог тимчасових файлів, не worktree; тайм-аут
   30 с; відмова ніколи не перериває виконання). Якщо help рекламує
   `--format … json`, до аргументів додається `--format json`, і після завершення
   перший рядок stdout перевіряється на типізовану JSON-подію: `OK: Agent
   output format: STRUCTURED events (--format json)` або `WARN: Agent output
   format: PLAIN fallback`. Якщо help не рекламує
   формат — виконання йде у звичайному (текстовому) режимі, і це фіксується
   у журналі. Пінг моделі (Stage 1) завжди виконується без `--format json`,
   бо перевіряє звичайний текст `PONG`. Поведінка не залежить від здогадок
   про конкретну версію CLI: рішення ухвалюється за фактичним help.
   Вихідні потоки читаються окремими потоками й транслюються в консоль та
   журнал у міру надходження (див. §3); stdout і stderr не втрачаються.
7. **Перевірка результату.** Код виконання і **коди завершення кожної команди
   верифікації**: `git status --porcelain` (має бути `0`), `git diff --check HEAD`
   (`0` або `2`) і `git diff --stat HEAD` (`0`). Diff виконується від `HEAD`,
   тому бачить **staged і змінені в робочому дереві** файли; `status` додатково
   бачить **untracked** — усі три категорії рахуються окремо і друкуються у
   журналі (`X staged, Y modified in worktree, Z untracked`).
   Будь-який неочікуваний код завершення (наприклад `128`) → стан невідомий →
   `ERROR`, код 1: **успіх не оголошується, якщо перевірки не завершилися
   коректно**. **Текстова заява моделі не є доказом.** Вихід 0 без змін →
   `NO_CHANGES` (не успіх). Головний клон має лишатися чистим.
8. **Прибирання.** Звільнення lock — у **вкладеному `finally`**, тобто відбувається
   завжди, навіть якщо крок прибирання кинув виняток (невдала перевірка стану
   чи видалення не пропускає звільнення). Worktree видаляється **лише коли його
   стан відомий і він порожній** (git-команди верифікації завершилися успішно і
   змін немає в усіх трьох категоріях). Якщо стан **невідомий** (невдача
   команди верифікації) або worktree **містить зміни** — він **зберігається**
   для огляду (`Worktree KEPT for inspection`), `--force` не застосовується
   ніколи, дані не видаляються примусово.
9. **Звіт.** `Stage 2 result: <SUCCESS | NO_CHANGES | ERROR | TIMEOUT | REFUSED>`.
   Коди виходу: `0` — SUCCESS/NO_CHANGES, `1` — ERROR, `2` — TIMEOUT,
   `4` — REFUSED (перевірка безпеки), `1` — зупинка до виконання (префлайт).

## 5. Журнал

Каталог із конфігурації (`LogDir`), за замовчуванням:

```
C:\Users\Admin\Documents\LyServerDispatcherLogs\dispatcher-<РРРРММДД-ГГММСС>.log
```

У журналі фіксуються: ідентифікатор задачі, базовий SHA, створення worktree,
команди, коди завершення, тайм-аути, результати перевірок, стан lock, а також
**живі вихідні рядки агента** (stdout/stderr) під час Stage 1 (пінг) і Stage 2
(виконання). Формат рядка журналу:

```
<РРРР-ММ-ДД ГГ:ММ:СС> [<рівень>] <текст>
```

де `<рівень>` — `INFO`/`WARN`/`ERROR` (рядки dispatcher'а), `OUT` (stdout
агента) або `ERR` (stderr агента). Кожен рядок виводу з'являється в
консолі та в журналі з однаковою міткою часу. Секрети й токени у журналах та
документації відсутні.

Перевірка успішного запуску Stage 1:

- останній рядок `=== Dispatcher finished (stage 1) ===`;
- `Preview completed. No claims, branches, sessions, or GitHub changes were made.`;
- відсутні рядки `[ERROR]`.

## 6. Типові помилки

| Повідомлення | Причина / дія |
|---|---|
| `another dispatcher instance is active (pid=…, host=…, age=…s)` | Запущено інший екземпляр (живий локальний PID). Дочекайтеся завершення. Після аварії з мертвим локальним процесом lock забирається одразу, без очікування; вік діє лише для чужого/невідомого хоста або неповного/нечитабельного вмісту. |
| `TaskSource=Local requires LocalTaskFile` / `BaseBranch` | Неповний конфіг тестового режиму. |
| `AgentCommand must be a plain command name` | У `AgentCommand` припустимі лише літери, цифри, `. _ -`. |
| `REFUSED: untrusted task text: …` | Опис Issue містить заборонену директиву. Це правило безпеки; приберіть її з тексту задачі самі, dispatcher не обходить її. |
| `REFUSED: issue #… is not open …` / `lost the '…' label` / `carries '…' label (concurrent claim)` | Повторна перевірка задачі перед виконанням: вона закрита, втратила мітку або вже заявлена іншим екземпляром. |
| `REFUSED: task requires base SHA … but the verified base is …` | База не збігається з вимогою задачі. Оновіть базу або текст задачі вручну. |
| `REFUSED: worktree path must be OUTSIDE the repository: …` | Небезпечний шлях worktree — перевірку обійти не можна. |
| `Main clone working tree must be clean before the dispatcher runs` | Приберіть зміни в головному клоні перед запуском dispatcher (тести цього не вимагають: вони працюють із тимчасовим репозиторієм). |
| `Worktree KEPT for inspection (state UNKNOWN: …)` / `(it contains changes: …)` | Стан невідомий або є зміни — worktree збережено для огляду (примусово не видаляється). |
| `ERROR: verification did not complete, worktree state unknown: …` | git-команда верифікації завершилася неочікуваним кодом — успіх не оголошується. |
| `TIMEOUT: agent exceeded …` | Виконання перевищило `TaskTimeoutSec`; дерево процесів убито. |
| `live output stream did not reach EOF in time; captured output may be incomplete …` | Після завершення процесу потік читання не дійшов EOF за відведений граничний час (30 с) — можливий неповний вивід. Це попередження, а не помилка: результат виконання не змінюється. |
| `Agent output format: STRUCTURED events (--format json)` / `Agent output format: PLAIN fallback …` | Підсумок вибору формату виводу за `run --help` агента: `STRUCTURED` — CLI рекламує `--format json` і перший рядок stdout є типізованою подією; `PLAIN` — help не рекламує формат (або відмовився/перевищив тайм-аут), виконання йде у звичайному текстовому режимі. |
| `Structured format was requested but stdout does not start with a typed event …` / `… produced no stdout lines to validate.` | `--format json` було додано за help, але фактичний вивід не є JSON-подіями — dispatcher позначає його як діагностичний текстовий вивід (fallback), виконання триває. |
| `LocalTaskFile not found` / `is not valid JSON` | Шлях або JSON невалідні. |

## 7. Обмеження безпеки (Stage 1 і Stage 2)

Без окремого дозволу заборонено і **не реалізовано** в коді:

- `git push`; створення PR; зливання гілок;
- закриття Issues, зміна міток/статусів/коментарів GitHub;
- запуск реального завдання з GitHub через OpenCode;
- зміна файлів поза репозиторієм (крім передбачених журналів і тимчасових
  каталогів); видалення чи переписування наявних комітів;
- автозлиття PR — заборонене завжди.

Недовірений текст (опис Issue, коментарі, відповіді моделі) ніколи не є
джерелом дозволів: він лише дані, які перевіряються, а не інструкції.
